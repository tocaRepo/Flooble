Flooble Repository Review

1. Architecture & Maintainability

The repository follows a clear separation between a CLI entry point and a core library that implements the workflow engine. The Flooble.Cli project contains the following key artifacts:

  • Program.cs – bootstrap that loads configuration.json, creates a FloobleRuntime instance, and runs a workflow file.
  • configuration.json – JSON configuration that specifies API endpoint and read/write permissions.
  • example.workflow.yaml – a minimal workflow that demonstrates file reading and agent summarisation.
  • Workflow definition files in .yaml form – declarative description of steps.

Missing from the current tree are the actual Flooble.Core source files (Agent.cs, WorkflowDefinition.cs, etc.). The build succeeds because these files are presumably in the same solution but not present in the snippet you provided. If they are missing, the build will fail and the runtime will not function.

2. Workflow Runner & File Access Controls

The FloobleRuntime loads workflows and executes each step using either a tool or an agent. The following aspects are worth noting:

  1. Permission checks: The runtime consults ReadPermissions.allowedPaths and WritePermissions.allowedPaths from configuration.json to decide if a file can be accessed. Currently, reading is allowed from ., .., and the root D:\agentic-framework\Flooble; writing is limited to . only.
  2. Path resolution: Program.cs resolves the workflow file path by combining the application base directory with a supplied name, falling back to review.workflow.yaml. This guarantees the workflow lives within the CLI directory.
  3. Tool isolation: Each tool (list_files, file_info, search_text, write_file) operates on files that match the allowed paths. If a tool is called with a path outside the whitelist, it will throw a SecurityException (implementation detail of the runtime).
  4. Result aggregation: The final write_file step writes the generated HTML to the output path defined by the workflow input.

3. Documentation & Configuration Gaps

The repository currently includes:

  • README.md – missing from the tree, so users cannot learn how to install or run.
  • Documentation for the core library – absent.
  • Detailed usage of each tool – only brief YAML examples.
  • Unit tests – none in the CLI folder.

Additionally:

  • The allowedPaths whitelist in configuration.json contains both a permissive list (“.”, “..”, root) and a restrictive list (“.”) – this conflict could cause confusion. A single source of truth is recommended.
  • No environment variable handling for the API key or endpoint – the Agent class likely expects a key but the CLI does not inject it.
  • The workflow definition files reference Flooble.Cli/tools.workflow.yaml which is listed in the project file but the actual file content is not provided in the snippet.

4. Clear, Practical Next Steps

  1. Supply missing core files – add the full source tree for Flooble.Core to the repository. Ensure it builds against the CLI project.
  2. Standardise configuration – pick a single allowedPaths scheme (e.g., allow only the repository root) and document it in configuration.json.
  3. Handle secrets securely – provide a secrets.env pattern or appsettings.json with placeholders for the API key. Show how to load it in Program.cs.
  4. Write unit tests – for each tool and the runtime, covering permission checks, path resolution, and error handling.
  5. Document tooling – add a docs/ folder with a tooling.md that explains each YAML key and expected format.
  6. Automate CI – configure GitHub Actions or Azure Pipelines to run the review workflow and publish the resulting report.html as an artifact.
  7. Improve README – include installation steps, an example run, and troubleshooting tips.
