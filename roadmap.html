Flooble Roadmap Report

From WPF chat prototype to cross-platform agent workbench.

This roadmap is based on the current repository shape: a .NET 10 solution with Flooble.Core, Flooble.Tools, Flooble.Cli, and a new Flooble.GUI WPF chat app. The immediate product goal is to preserve the deterministic YAML workflow runner while turning Flooble into a usable GUI/web workbench for agent-assisted local automation.

Current visible product CLI workflow runner plus a Windows-only WPF chat UI that calls AgentChatService.
Best next architecture move Keep runtime/tool execution in Flooble.Core; move UI to Blazor Web App for Unix compatibility.
Main compatibility risk Flooble.GUI targets net10.0-windows and uses WPF, so it will not run on Linux/Unix.
Recommended roadmap path Stabilize core, add tests and validation, then build Flooble.Web as the cross-platform GUI.

Repository assessment

The repo has moved beyond the earlier CLI-only state. It now includes a reusable runtime service, structured workflow events, and a WPF chat GUI. It still lacks a test suite, workflow validation, a proper run-history model, and a cross-platform GUI surface.

Architecture direction

Keep Core UI-agnostic

Flooble.Core should expose runtime, validation, tool registry, events, chat sessions, and history models without depending on WPF, Blazor, or console APIs.

Keep Tools permission-bound

Flooble.Tools should own local file access and produce explainable denied-access diagnostics. This will matter more in browser-based UX.

Make Web the primary GUI

A Blazor Web App can run on Windows, Linux, and macOS as an ASP.NET Core app, while users access it through a browser.

Treat WPF as optional

The current WPF UI can remain a Windows shell or prototype, but should not be the main GUI if Unix support matters.

Roadmap

Phase 1: Stabilize

Add tests, validation, and permission diagnostics around the current runtime and tools.

Phase 2: Cross-platform GUI

Create Flooble.Web with Blazor/Razor as the primary GUI surface.

Phase 3: Workbench

Add workflow editor, live diagnostics, event stream, run history, and reports.

Phase 4: Release

Package, document, and harden Flooble for local users and repeatable agent workflows.

1. Add a test suite for Core and Tools

Phase 1QualityHigh priority

Flooble now has enough runtime behavior that changes are risky without tests. Start with workflow interpretation, event emission, tool permissions, and path handling.

2. Add workflow validation and diagnostics

Phase 1AuthoringHigh priority

Move common workflow errors from runtime exceptions to pre-run diagnostics that can be shown in CLI, WPF, and Blazor UI.

3. Add permission inspector and Unix path tests

Phase 1SafetyUnix readiness

The tools currently normalize and compare paths with .NET APIs. Add explicit tests for Windows paths, Unix paths, relative paths, symlinks if supported, and allowed-path boundaries.

4. Create Flooble.Web as the primary GUI

Phase 2BlazorCross-platform

Build a Blazor/Razor interface with chat, configuration health, workflow runner, event log, and errors. This should replace WPF as the main cross-platform UI.

5. Add durable chat sessions

Phase 2Agent UX

The current chat service sends a single message to an agent. Add session state, transcript storage, system instructions, and optional tool visibility.

6. Add workflow runner UI with live events

Phase 3Workbench

Use existing WorkflowRunEvent callbacks to show step progress, output lengths, failures, and final results in the web UI.

7. Add workflow editor and templates

Phase 3Authoring

Provide a YAML editor with templates, validation, save-as, and run-current-document behavior.

8. Add run history and report export

Phase 3Reports

Persist run summaries and allow report export so the existing stale report.html pattern becomes a repeatable feature.

9. Add tool registry metadata

Phase 4Extensibility

Centralize tool names, descriptions, arguments, safety rules, and handlers so validation and UI help are generated from one place.

10. Release and documentation pass

Phase 4Release

Document CLI, Web GUI, optional WPF GUI, configuration, secrets, permission model, examples, testing, and packaging.

GUI Unix compatibility assessment

Verdict: the current Flooble.GUI cannot be the Unix/Linux GUI because it is WPF and targets net10.0-windows. If Unix compatibility matters, switch the primary GUI to a Blazor/Razor web app and keep WPF only as an optional Windows desktop shell.

Option Unix/Linux viability Pros Cons Recommendation
Keep current WPF Flooble.GUI No Already exists. Good Windows desktop prototype. Familiar XAML style. Windows-only. net10.0-windows. Cannot satisfy Unix/Linux GUI requirement. Keep only as optional Windows shell or delete later if maintenance cost grows.
Blazor Web App / Razor Components Yes Runs as ASP.NET Core, browser-based, works well on Windows/Linux/macOS servers, good for local workbench UX. Needs local web server. Browser security model changes some file-picker expectations. Best primary path. Create Flooble.Web.
.NET MAUI Blazor Hybrid Not for Linux desktop Reusable Razor components across supported MAUI targets. Good for Windows/macOS/mobile. Official MAUI desktop platform list excludes Linux desktop. Does not solve Unix/Linux local desktop goal. Do not choose for Linux compatibility.
WPF + BlazorWebView No Could reuse Razor components inside Windows WPF. Still WPF/Windows. Good migration bridge, not Unix compatibility. Only useful if keeping Windows desktop UX while sharing Razor components.
Avalonia Yes Cross-platform native desktop; familiar to WPF/XAML developers; supports Linux desktop. Additional framework and different APIs/styles. Less directly aligned with Razor/Blazor request. Good alternative if native desktop is more important than browser-based UX.

Decision

Switch primary GUI to Blazor/Razor

Flooble is an automation workbench, not a graphics-heavy native desktop app. A local browser UI is enough for chat, workflow editing, diagnostics, reports, run history, and permission inspection. It also keeps the UI cross-platform.

Do not build more WPF-only features first

Further WPF investment increases migration cost. Move the next GUI work to Flooble.Web; reuse Flooble.Core, AgentChatService, and FloobleRuntime.

Suggested migration sequence

  1. Leave Flooble.GUI untouched for now.
  2. Create Flooble.Web as a Blazor Web App.
  3. Move chat UI behavior into web components backed by AgentChatService.
  4. Add workflow runner page backed by FloobleRuntime and WorkflowRunEvent.
  5. Add workflow editor, validation, and reports in the web app.
  6. After web feature parity, decide whether WPF remains useful as a Windows-only shell.

Compatibility notes

  • WPF only runs on Windows, despite .NET itself being cross-platform.
  • ASP.NET Core is cross-platform and includes Blazor as a web UI option.
  • Blazor Web Apps can run locally and be accessed through a browser, which makes Unix/Linux support straightforward.
  • MAUI supports Windows, macOS, Android, and iOS targets, but not Linux desktop as a first-class supported platform.
  • Blazor Hybrid is useful for native shells, but not necessary for Flooble's first cross-platform GUI.

Suggested next move: add the test suite and validator first, then create Flooble.Web. Do not expand the WPF GUI until the project has decided whether Windows-only desktop support is still worth maintaining.
